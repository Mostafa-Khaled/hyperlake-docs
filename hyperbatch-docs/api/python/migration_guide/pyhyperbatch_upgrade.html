Upgrading PyHyperBatch#

Upgrading from PyHyperBatch 4.1 to 4.2#

  • In HyperBatch 4.2, the minimum supported version for PyArrow has been raised from 15.0.0 to 18.0.0 in PyHyperBatch.

  • In HyperBatch 4.2, DataFrame.__getattr__ on HyperBatch Connect Python Client no longer eagerly validate the column name. To restore the legacy behavior, set PYHYPERBATCH_VALIDATE_COLUMN_NAME_LEGACY environment variable to 1.

  • In HyperBatch 4.2, columnar data exchange between PyHyperBatch and the JVM uses Apache Arrow by default. The configuration hyperbatch.sql.execution.arrow.pyhyperbatch.enabled now defaults to true. To restore the legacy (non-Arrow) row-based data exchange, set hyperbatch.sql.execution.arrow.pyhyperbatch.enabled to false.

  • In HyperBatch 4.2, regular Python UDFs are Arrow-optimized by default. The configuration hyperbatch.sql.execution.pythonUDF.arrow.enabled now defaults to true. To restore the legacy behavior for Python UDF execution, set hyperbatch.sql.execution.pythonUDF.arrow.enabled to false.

  • In HyperBatch 4.2, regular Python UDTFs are Arrow-optimized by default. The configuration hyperbatch.sql.execution.pythonUDTF.arrow.enabled now defaults to true. To restore the legacy behavior for Python UDTF execution, set hyperbatch.sql.execution.pythonUDTF.arrow.enabled to false.

  • In HyperBatch 4.2, PyPy is no longer officially supported. Run PyHyperBatch on CPython instead.

  • In HyperBatch 4.2, HyperBatchSession.createDataFrame from a NumPy ndarray requires PyArrow (instead of pandas) and converts the array directly to Arrow rather than through pandas. Install PyArrow; if you previously ran with Arrow disabled and relied on NumPy-dtype-based schema inference, review the inferred schema, as it now follows Arrow’s type mapping.

  • In HyperBatch 4.2, when a pandas UDF receives a nullable integer column whose batch contains nulls, the column is delivered as a pandas nullable integer extension dtype (Int8/Int16/Int32/Int64) instead of float64. Update UDF code that assumed float64 input for nullable integer columns.

  • In HyperBatch 4.2, DataFrame.drop and Series.drop in pandas API on HyperBatch raise a KeyError when any of the specified labels is missing, instead of only when all of them are missing, matching pandas. Make sure all labels exist before dropping, filter to existing labels, or pass errors="ignore".

  • In HyperBatch 4.2, a Python Data Source whose returned Arrow data has column types that do not match its declared schema fails with DATA_SOURCE_RETURN_SCHEMA_MISMATCH (column count and name mismatches already raised this error in earlier versions). Make the data source return data whose types match its declared schema.

  • In HyperBatch 4.2, a SimpleDataSourceStreamReader whose read() returns a non-empty batch without advancing the end offset past the start offset fails with SIMPLE_STREAM_READER_OFFSET_DID_NOT_ADVANCE, instead of reprocessing the same batch and growing the prefetch cache without bound. Ensure the returned end offset advances past the last record.

Upgrading from PyHyperBatch 4.0 to 4.1#

  • In HyperBatch 4.1, Python 3.9 support was dropped in PyHyperBatch.

  • In HyperBatch 4.1, the minimum supported version for PyArrow has been raised from 11.0.0 to 15.0.0 in PyHyperBatch.

  • In HyperBatch 4.1, the minimum supported version for Pandas has been raised from 2.0.0 to 2.2.0 in PyHyperBatch.

  • In HyperBatch 4.1, DataFrame.__getitem__ on HyperBatch Connect Python Client no longer eagerly validate the column name. To restore the legacy behavior, set PYHYPERBATCH_VALIDATE_COLUMN_NAME_LEGACY environment variable to 1.

  • In HyperBatch 4.1, Arrow-optimized Python UDF supports UDT input / output instead of falling back to the regular UDF. To restore the legacy behavior, set hyperbatch.sql.execution.pythonUDF.arrow.legacy.fallbackOnUDT to true.

  • In HyperBatch 4.1, unnecessary conversion to pandas instances is removed when hyperbatch.sql.execution.pythonUDF.arrow.enabled is enabled. As a result, the type coercion changes when the produced output has a schema different from the specified schema. To restore the previous behavior, enable hyperbatch.sql.legacy.execution.pythonUDF.pandas.conversion.enabled.

  • In HyperBatch 4.1, unnecessary conversion to pandas instances is removed when hyperbatch.sql.execution.pythonUDTF.arrow.enabled is enabled. As a result, the type coercion changes when the produced output has a schema different from the specified schema. To restore the previous behavior, enable hyperbatch.sql.legacy.execution.pythonUDTF.pandas.conversion.enabled.

  • In HyperBatch 4.1, the data type BinaryType is by default mapped consistently to Python bytes in PyHyperBatch. To restore the previous behavior, set hyperbatch.sql.execution.pyhyperbatch.binaryAsBytes to false. The behavior before HyperBatch 4.1.0 is illustrated in the following table:

    Case

    Python type for BinaryType

    Regular UDF and UDTF without Arrow optimization

    bytearray

    DataFrame APIs (both HyperBatch Classic and HyperBatch Connect)

    bytearray

    Data sources

    bytearray

    Arrow-optimized UDF and UDTF with unnecessary conversion to pandas instances

    bytes

  • In HyperBatch 4.1, the hyperbatch.sql.execution.pandas.convertToArrowArraySafely configuration is enabled by default. When this setting is enabled, PyArrow raises errors for unsafe conversions such as integer overflows, floating point truncation, and loss of precision. This change affects the return data serialization of arrow-enabled UDFs/pandas_udfs, and the creation of PyHyperBatch DataFrames. To restore the previous behavior, set the configuration to false.

  • In HyperBatch 4.1, pandas API on HyperBatch works under ANSI mode when compute.ansi_mode_support is set to True (default). The safeguard option compute.fail_on_ansi_mode remains available, but it only takes effect when compute.ansi_mode_support is False.

Upgrading from PyHyperBatch 3.5 to 4.0#

  • In HyperBatch 4.0, Python 3.8 support was dropped in PyHyperBatch.

  • In HyperBatch 4.0, the minimum supported version for Pandas has been raised from 1.0.5 to 2.0.0 in PyHyperBatch.

  • In HyperBatch 4.0, the minimum supported version for Numpy has been raised from 1.15 to 1.21 in PyHyperBatch.

  • In HyperBatch 4.0, the minimum supported version for PyArrow has been raised from 4.0.0 to 11.0.0 in PyHyperBatch.

  • In HyperBatch 4.0, Int64Index and Float64Index have been removed from pandas API on HyperBatch, Index should be used directly.

  • In HyperBatch 4.0, DataFrame.iteritems has been removed from pandas API on HyperBatch, use DataFrame.items instead.

  • In HyperBatch 4.0, Series.iteritems has been removed from pandas API on HyperBatch, use Series.items instead.

  • In HyperBatch 4.0, DataFrame.append has been removed from pandas API on HyperBatch, use ps.concat instead.

  • In HyperBatch 4.0, Series.append has been removed from pandas API on HyperBatch, use ps.concat instead.

  • In HyperBatch 4.0, DataFrame.mad has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, Series.mad has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, na_sentinel parameter from Index.factorize and Series.factorize has been removed from pandas API on HyperBatch, use use_na_sentinel instead.

  • In HyperBatch 4.0, inplace parameter from Categorical.add_categories, Categorical.remove_categories, Categorical.set_categories, Categorical.rename_categories, Categorical.reorder_categories, Categorical.as_ordered, Categorical.as_unordered have been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, inplace parameter from CategoricalIndex.add_categories, CategoricalIndex.remove_categories, CategoricalIndex.remove_unused_categories, CategoricalIndex.set_categories, CategoricalIndex.rename_categories, CategoricalIndex.reorder_categories, CategoricalIndex.as_ordered, CategoricalIndex.as_unordered have been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, closed parameter from ps.date_range has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, include_start and include_end parameters from DataFrame.between_time have been removed from pandas API on HyperBatch, use inclusive instead.

  • In HyperBatch 4.0, include_start and include_end parameters from Series.between_time have been removed from pandas API on HyperBatch, use inclusive instead.

  • In HyperBatch 4.0, the various datetime attributes of DatetimeIndex (day, month, year etc.) are now int32 instead of int64 from pandas API on HyperBatch.

  • In HyperBatch 4.0, sort_columns parameter from DataFrame.plot and Series.plot has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, the default value of regex parameter for Series.str.replace has been changed from True to False from pandas API on HyperBatch. Additionally, a single character pat with regex=True is now treated as a regular expression instead of a string literal.

  • In HyperBatch 4.0, the resulting name from value_counts for all objects sets to 'count' (or 'proportion' if normalize=True was passed) from pandas API on HyperBatch, and the index will be named after the original object.

  • In HyperBatch 4.0, squeeze parameter from ps.read_csv and ps.read_excel has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, null_counts parameter from DataFrame.info has been removed from pandas API on HyperBatch, use show_counts instead.

  • In HyperBatch 4.0, the result of MultiIndex.append does not keep the index names from pandas API on HyperBatch.

  • In HyperBatch 4.0, DataFrameGroupBy.agg with lists respecting as_index=False from pandas API on HyperBatch.

  • In HyperBatch 4.0, DataFrame.stack guarantees the order of existing columns instead of sorting them lexicographically from pandas API on HyperBatch.

  • In HyperBatch 4.0, True or False to inclusive parameter from Series.between has been removed from pandas API on HyperBatch, use both or neither instead respectively.

  • In HyperBatch 4.0, Index.asi8 has been removed from pandas API on HyperBatch, use Index.astype instead.

  • In HyperBatch 4.0, Index.is_type_compatible has been removed from pandas API on HyperBatch, use Index.isin instead.

  • In HyperBatch 4.0, col_space parameter from DataFrame.to_latex and Series.to_latex has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, DataFrame.to_hyperbatch_io has been removed from pandas API on HyperBatch, use DataFrame.hyperbatch.to_hyperbatch_io instead.

  • In HyperBatch 4.0, Series.is_monotonic and Index.is_monotonic have been removed from pandas API on HyperBatch, use Series.is_monotonic_increasing or Index.is_monotonic_increasing instead respectively.

  • In HyperBatch 4.0, DataFrame.get_dtype_counts has been removed from pandas API on HyperBatch, use DataFrame.dtypes.value_counts() instead.

  • In HyperBatch 4.0, encoding parameter from DataFrame.to_excel and Series.to_excel have been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, verbose parameter from DataFrame.to_excel and Series.to_excel have been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, mangle_dupe_cols parameter from read_csv has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, DataFrameGroupBy.backfill has been removed from pandas API on HyperBatch, use DataFrameGroupBy.bfill instead.

  • In HyperBatch 4.0, DataFrameGroupBy.pad has been removed from pandas API on HyperBatch, use DataFrameGroupBy.ffill instead.

  • In HyperBatch 4.0, Index.is_all_dates has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, convert_float parameter from read_excel has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, mangle_dupe_cols parameter from read_excel has been removed from pandas API on HyperBatch.

  • In HyperBatch 4.0, DataFrame.koalas has been removed from pandas API on HyperBatch, use DataFrame.pandas_on_hyperbatch instead.

  • In HyperBatch 4.0, DataFrame.to_koalas has been removed from PyHyperBatch, use DataFrame.pandas_api instead.

  • In HyperBatch 4.0, DataFrame.to_pandas_on_hyperbatch has been removed from PyHyperBatch, use DataFrame.pandas_api instead.

  • In HyperBatch 4.0, DatatimeIndex.week and DatatimeIndex.weekofyear have been removed from Pandas API on HyperBatch, use DatetimeIndex.isocalendar().week instead.

  • In HyperBatch 4.0, Series.dt.week and Series.dt.weekofyear have been removed from Pandas API on HyperBatch, use Series.dt.isocalendar().week instead.

  • In HyperBatch 4.0, when applying astype to a decimal type object, the existing missing value is changed to True instead of False from Pandas API on HyperBatch.

  • In HyperBatch 4.0, pyhyperbatch.testing.assertPandasOnHyperBatchEqual has been removed from Pandas API on HyperBatch, use pyhyperbatch.pandas.testing.assert_frame_equal instead.

  • In HyperBatch 4.0, the aliases Y, M, H, T, S have been deprecated from Pandas API on HyperBatch, use YE, ME, h, min, s instead respectively.

  • In HyperBatch 4.0, the schema of a map column is inferred by merging the schemas of all pairs in the map. To restore the previous behavior where the schema is only inferred from the first non-null pair, you can set hyperbatch.sql.pyhyperbatch.legacy.inferMapTypeFromFirstPair.enabled to true.

  • In HyperBatch 4.0, compute.ops_on_diff_frames is on by default. To restore the previous behavior, set compute.ops_on_diff_frames to false.

  • In HyperBatch 4.0, the data type YearMonthIntervalType in DataFrame.collect no longer returns the underlying integers. To restore the previous behavior, set PYHYPERBATCH_YM_INTERVAL_LEGACY environment variable to 1.

  • In HyperBatch 4.0, items other than functions (e.g. DataFrame, Column, StructType) have been removed from the wildcard import from pyhyperbatch.sql.functions import *, you should import these items from proper modules (e.g. from pyhyperbatch.sql import DataFrame, Column, from pyhyperbatch.sql.types import StructType).

  • In HyperBatch 4.0, pandas API on HyperBatch will raise an exception if the underlying HyperBatch is working with ANSI mode enabled that is enabled by default, as it will not work properly with ANSI mode. To make it work, you need to explicitly disable ANSI mode by setting hyperbatch.sql.ansi.enabled to false. Alternatively you can set a pandas-on-hyperbatch option compute.fail_on_ansi_mode to False to force it to work, although it can cause unexpected behavior.

Upgrading from PyHyperBatch 3.3 to 3.4#

  • In HyperBatch 3.4, the schema of an array column is inferred by merging the schemas of all elements in the array. To restore the previous behavior where the schema is only inferred from the first element, you can set hyperbatch.sql.pyhyperbatch.legacy.inferArrayTypeFromFirstElement.enabled to true.

  • In HyperBatch 3.4, if Pandas on HyperBatch API Groupby.apply’s func parameter return type is not specified and compute.shortcut_limit is set to 0, the sampling rows will be set to 2 (ensure sampling rows always >= 2) to make sure infer schema is accurate.

  • In HyperBatch 3.4, if Pandas on HyperBatch API Index.insert is out of bounds, will raise IndexError with index {} is out of bounds for axis 0 with size {} to follow pandas 1.4 behavior.

  • In HyperBatch 3.4, the series name will be preserved in Pandas on HyperBatch API Series.mode to follow pandas 1.4 behavior.

  • In HyperBatch 3.4, the Pandas on HyperBatch API Index.__setitem__ will first to check value type is Column type to avoid raising unexpected ValueError in is_list_like like Cannot convert column into bool: please use ‘&’ for ‘and’, ‘|’ for ‘or’, ‘~’ for ‘not’ when building DataFrame boolean expressions..

  • In HyperBatch 3.4, the Pandas on HyperBatch API astype('category') will also refresh categories.dtype according to original data dtype to follow pandas 1.4 behavior.

  • In HyperBatch 3.4, the Pandas on HyperBatch API supports groupby positional indexing in GroupBy.head and GroupBy.tail to follow pandas 1.4. Negative arguments now work correctly and result in ranges relative to the end and start of each group, Previously, negative arguments returned empty frames.

  • In HyperBatch 3.4, the infer schema process of groupby.apply in Pandas on HyperBatch, will first infer the pandas type to ensure the accuracy of the pandas dtype as much as possible.

  • In HyperBatch 3.4, the Series.concat sort parameter will be respected to follow pandas 1.4 behaviors.

  • In HyperBatch 3.4, the DataFrame.__setitem__ will make a copy and replace pre-existing arrays, which will NOT be over-written to follow pandas 1.4 behaviors.

  • In HyperBatch 3.4, the HyperBatchSession.sql and the Pandas on HyperBatch API sql have got new parameter args which provides binding of named parameters to their SQL literals.

  • In HyperBatch 3.4, Pandas API on HyperBatch follows for the pandas 2.0, and some APIs were deprecated or removed in HyperBatch 3.4 according to the changes made in pandas 2.0. Please refer to the [release notes of pandas](https://pandas.pydata.org/docs/dev/whatsnew/) for more details.

  • In HyperBatch 3.4, the custom monkey-patch of collections.namedtuple was removed, and cloudpickle was used by default. To restore the previous behavior for any relevant pickling issue of collections.namedtuple, set PYHYPERBATCH_ENABLE_NAMEDTUPLE_PATCH environment variable to 1.

Upgrading from PyHyperBatch 3.2 to 3.3#

  • In HyperBatch 3.3, the pyhyperbatch.pandas.sql method follows [the standard Python string formatter](https://docs.python.org/3/library/string.html#format-string-syntax). To restore the previous behavior, set PYHYPERBATCH_PANDAS_SQL_LEGACY environment variable to 1.

  • In HyperBatch 3.3, the drop method of pandas API on HyperBatch DataFrame supports dropping rows by index, and sets dropping by index instead of column by default.

  • In HyperBatch 3.3, PyHyperBatch upgrades Pandas version, the new minimum required version changes from 0.23.2 to 1.0.5.

  • In HyperBatch 3.3, the repr return values of SQL DataTypes have been changed to yield an object with the same value when passed to eval.

Upgrading from PyHyperBatch 3.1 to 3.2#

  • In HyperBatch 3.2, the PyHyperBatch methods from sql, ml, hyperbatch_on_pandas modules raise the TypeError instead of ValueError when are applied to a param of inappropriate type.

  • In HyperBatch 3.2, the traceback from Python UDFs, pandas UDFs and pandas function APIs are simplified by default without the traceback from the internal Python workers. In HyperBatch 3.1 or earlier, the traceback from Python workers was printed out. To restore the behavior before HyperBatch 3.2, you can set hyperbatch.sql.execution.pyhyperbatch.udf.simplifiedTraceback.enabled to false.

  • In HyperBatch 3.2, pinned thread mode is enabled by default to map each Python thread to the corresponding JVM thread. Previously, one JVM thread could be reused for multiple Python threads, which resulted in one JVM thread local being shared to multiple Python threads. Also, note that now pyhyperbatch.InheritableThread or pyhyperbatch.inheritable_thread_target is recommended to use together for a Python thread to properly inherit the inheritable attributes such as local properties in a JVM thread, and to avoid a potential resource leak issue. To restore the behavior before HyperBatch 3.2, you can set PYHYPERBATCH_PIN_THREAD environment variable to false.

Upgrading from PyHyperBatch 2.4 to 3.0#

  • In HyperBatch 3.0, PyHyperBatch requires a pandas version of 0.23.2 or higher to use pandas related functionality, such as toPandas, createDataFrame from pandas DataFrame, and so on.

  • In HyperBatch 3.0, PyHyperBatch requires a PyArrow version of 0.12.1 or higher to use PyArrow related functionality, such as pandas_udf, toPandas and createDataFrame with “hyperbatch.sql.execution.arrow.enabled=true”, etc.

  • In PyHyperBatch, when creating a HyperBatchSession with HyperBatchSession.builder.getOrCreate(), if there is an existing HyperBatchContext, the builder was trying to update the HyperBatchConf of the existing HyperBatchContext with configurations specified to the builder, but the HyperBatchContext is shared by all HyperBatchSession s, so we should not update them. In 3.0, the builder comes to not update the configurations. This is the same behavior as Java/Scala API in 2.3 and above. If you want to update them, you need to update them prior to creating a HyperBatchSession.

  • In PyHyperBatch, when Arrow optimization is enabled, if Arrow version is higher than 0.11.0, Arrow can perform safe type conversion when converting pandas.Series to an Arrow array during serialization. Arrow raises errors when detecting unsafe type conversions like overflow. You enable it by setting hyperbatch.sql.execution.pandas.convertToArrowArraySafely to true. The default setting is false. PyHyperBatch behavior for Arrow versions is illustrated in the following table:

    PyArrow version

    Integer overflow

    Floating point truncation

    0.11.0 and below

    Raise error

    Silently allows

    > 0.11.0, arrowSafeTypeConversion=false

    Silent overflow

    Silently allows

    > 0.11.0, arrowSafeTypeConversion=true

    Raise error

    Raise error

  • In HyperBatch 3.0, createDataFrame(..., verifySchema=True) validates LongType as well in PyHyperBatch. Previously, LongType was not verified and resulted in None in case the value overflows. To restore this behavior, verifySchema can be set to False to disable the validation.

  • As of HyperBatch 3.0, Row field names are no longer sorted alphabetically when constructing with named arguments for Python versions 3.6 and above, and the order of fields will match that as entered. To enable sorted fields by default, as in HyperBatch 2.4, set the environment variable PYHYPERBATCH_ROW_FIELD_SORTING_ENABLED to true for both executors and driver - this environment variable must be consistent on all executors and driver; otherwise, it may cause failures or incorrect answers. For Python versions less than 3.6, the field names will be sorted alphabetically as the only option.

  • In HyperBatch 3.0, pyhyperbatch.ml.param.shared.Has* mixins do not provide any set*(self, value) setter methods anymore, use the respective self.set(self.*, value) instead. See HYPERBATCH-29093 for details.

Upgrading from PyHyperBatch 2.3 to 2.4#

  • In PyHyperBatch, when Arrow optimization is enabled, previously toPandas just failed when Arrow optimization is unable to be used whereas createDataFrame from Pandas DataFrame allowed the fallback to non-optimization. Now, both toPandas and createDataFrame from Pandas DataFrame allow the fallback by default, which can be switched off by hyperbatch.sql.execution.arrow.fallback.enabled.

Upgrading from PyHyperBatch 2.3.0 to 2.3.1 and above#

  • As of version 2.3.1 Arrow functionality, including pandas_udf and toPandas()/createDataFrame() with hyperbatch.sql.execution.arrow.enabled set to True, has been marked as experimental. These are still evolving and not currently recommended for use in production.

Upgrading from PyHyperBatch 2.2 to 2.3#

  • In PyHyperBatch, now we need Pandas 0.19.2 or upper if you want to use Pandas related functionalities, such as toPandas, createDataFrame from Pandas DataFrame, etc.

  • In PyHyperBatch, the behavior of timestamp values for Pandas related functionalities was changed to respect session timezone. If you want to use the old behavior, you need to set a configuration hyperbatch.sql.execution.pandas.respectSessionTimeZone to False. See HYPERBATCH-22395 for details.

  • In PyHyperBatch, na.fill() or fillna also accepts boolean and replaces nulls with booleans. In prior HyperBatch versions, PyHyperBatch just ignores it and returns the original Dataset/DataFrame.

  • In PyHyperBatch, df.replace does not allow to omit value when to_replace is not a dictionary. Previously, value could be omitted in the other cases and had None by default, which is counterintuitive and error-prone.

Upgrading from PyHyperBatch 1.4 to 1.5#

  • Resolution of strings to columns in Python now supports using dots (.) to qualify the column or access nested values. For example df['table.column.nestedField']. However, this means that if your column name contains any dots you must now escape them using backticks (e.g., table.`column.with.dots`.nested).

  • DataFrame.withColumn method in PyHyperBatch supports adding a new column or replacing existing columns of the same name.

Upgrading from PyHyperBatch 1.0-1.2 to 1.3#

  • When using DataTypes in Python you will need to construct them (i.e. StringType()) instead of referencing a singleton.

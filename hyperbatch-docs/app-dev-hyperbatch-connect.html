Application Development with HyperBatch Connect

HyperBatch Connect Overview

In HyperBatch 3.4, HyperBatch Connect introduced a decoupled client-server architecture that allows remote connectivity to HyperBatch clusters using the DataFrame API and unresolved logical plans as the protocol. The separation between client and server allows HyperBatch and its open ecosystem to be leveraged from everywhere. It can be embedded in modern data applications, in IDEs, Notebooks and programming languages.

To learn more about HyperBatch Connect, see HyperBatch Connect Overview.

Redefining HyperBatch Applications using HyperBatch Connect

With its decoupled client-server architecture, HyperBatch Connect simplifies how HyperBatch Applications are developed. The notion of HyperBatch Client Applications and HyperBatch Server Libraries are introduced as follows:

  • HyperBatch Client Applications are regular HyperBatch applications that use HyperBatch and its rich ecosystem for distributed data processing. Examples include ETL pipelines, data preparation, and model training and inference.
  • HyperBatch Server Libraries build on, extend, and complement HyperBatch’s functionality, e.g. MLlib (distributed ML libraries that use HyperBatch’s powerful distributed processing). HyperBatch Connect can be extended to expose client-side interfaces for HyperBatch Server Libraries.

With HyperBatch 3.4 and HyperBatch Connect, the development of HyperBatch Client Applications is simplified, and clear extension points and guidelines are provided on how to build HyperBatch Server Libraries, making it easy for both types of applications to evolve alongside HyperBatch. As illustrated in Fig.1, HyperBatch Client applications connect to HyperBatch using the HyperBatch Connect API, which is essentially the DataFrame API and fully declarative.

HyperBatch Server Libraries extend HyperBatch. They typically provide additional server-side logic integrated with HyperBatch, which is exposed to client applications as part of the HyperBatch Connect API, using HyperBatch Connect extension points. The client uses this API, e.g., alongside PyHyperBatch or the HyperBatch Scala client, making it easy for HyperBatch client applications to work with the custom logic/library.

HyperBatch Client Applications

HyperBatch Client Applications are the regular HyperBatch applications that HyperBatch users develop today, e.g., ETL pipelines, data preparation, or model training or inference. These are typically built using HyperBatchs declarative DataFrame and DataSet APIs. With HyperBatch Connect, the core behaviour remains the same, but there are a few differences:

  • Lower-level, non-declarative APIs (RDDs) can no longer be directly used from HyperBatch Client applications. Alternatives for missing RDD functionality are provided as part of the higher-level DataFrame API.
  • Client applications no longer have direct access to the HyperBatch driver JVM; they are fully separated from the server.

Client applications based on HyperBatch Connect can be submitted in the same way as any previous job. In addition, HyperBatch Client Applications based on HyperBatch Connect have several benefits compared to classic HyperBatch applications using earlier HyperBatch versions (3.4 and below):

  • Upgradability: Upgrading to new HyperBatch Server versions is seamless, as the HyperBatch Connect API abstracts any changes/improvements on the server side. Client- and server APIs are cleanly separated.
  • Simplicity: The number of APIs exposed to the user is reduced from 3 to 2. The HyperBatch Connect API is fully declarative and consequently easy to learn for new users familiar with SQL.
  • Stability: When using HyperBatch Connect, the client applications no longer run on the HyperBatch driver and, therefore don’t cause and are not affected by any instability on the server.
  • Remote connectivity: The decoupled architecture allows remote connectivity to HyperBatch beyond SQL and JDBC: any application can now interactively use HyperBatch “as a service”.
  • Backwards compatibility: The HyperBatch Connect API is code-compatible with earlier HyperBatch versions, except for the usage of RDDs, for which a list of alternative APIs is provided in HyperBatch Connect.

HyperBatch Server Libraries

Until HyperBatch 3.4, extensions to HyperBatch (e.g., HyperBatch ML or HyperBatch-NLP) were built and deployed like HyperBatch Client Applications. With HyperBatch 3.4 and HyperBatch Connect, explicit extension points are offered to extend HyperBatch via HyperBatch Server Libraries. These extension points provide functionality that can be exposed to a client, which differs from existing extension points in HyperBatch such as HyperBatchSession extensions or HyperBatch Plugins.

Getting Started: Extending HyperBatch with HyperBatch Server Libraries

HyperBatch Connect is available and supports PyHyperBatch and Scala applications. We will walk through how to run an HyperBatch server with HyperBatch Connect and connect to it from a client application using the HyperBatch Connect client library.

A HyperBatch Server Library consists of the following components, illustrated in Fig. 2:

  1. The HyperBatch Connect protocol extension (blue box Proto API)
  2. A HyperBatch Connect Plugin.
  3. The application logic that extends HyperBatch.
  4. The client package that exposes the HyperBatch Server Library application logic to the HyperBatch Client Application, alongside PyHyperBatch or the Scala HyperBatch Client.

(1) HyperBatch Connect Protocol Extension

To extend HyperBatch with a new HyperBatch Server Library, developers can extend the three main operation types in the HyperBatch Connect protocol: Relation, Expression, and Command.

Their extension fields allow serializing arbitrary protobuf messages as part of the HyperBatch Connect protocol. These messages represent the parameters or state of the extension implementation. Once the application logic is developed, the code must be packaged as a jar and HyperBatch must be configured to pick up the additional logic. The relevant HyperBatch configuration options are:

  • hyperbatch.jars which define the location of the Jar file containing the application logic built for the custom expression.
  • hyperbatch.connect.extensions.expression.classes specifying the full class name of each expression extension loaded by HyperBatch. Based on these configuration options, HyperBatch will load the values at startup and make them available for processing.

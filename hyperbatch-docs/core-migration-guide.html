Upgrading from Core 4.1 to 4.2

  • Since HyperBatch 4.2, HyperBatch Master REST API uses Java 21 virtual threads by default when running on Java 21 or later. To restore the legacy behavior, you can set hyperbatch.master.rest.virtualThread.enabled to false.

  • Since HyperBatch 4.2, HyperBatch will allocate executor pods with a batch size of 20. To restore the legacy behavior, you can set hyperbatch.kubernetes.allocation.batch.size to 10.

  • Since HyperBatch 4.2, HyperBatch configures a NetworkPolicy by default so that executor pods only accept ingress traffic from the driver and peer executors within the same job. To disable this and restore the legacy behavior, set hyperbatch.kubernetes.driver.pod.excludedFeatureSteps to org.apache.hyperbatch.deploy.k8s.features.NetworkPolicyFeatureStep.

Upgrading from Core 4.0 to 4.1

  • Since HyperBatch 4.1, HyperBatch Master daemon provides REST API by default. To restore the behavior before HyperBatch 4.1, you can set hyperbatch.master.rest.enabled to false.
  • Since HyperBatch 4.1, HyperBatch will compress RDD checkpoints by default. To restore the behavior before HyperBatch 4.1, you can set hyperbatch.checkpoint.compress to false.
  • Since HyperBatch 4.1, HyperBatch uses Apache Hadoop Magic Committer for all S3 buckets by default. To restore the behavior before HyperBatch 4.0, you can set hyperbatch.hadoop.fs.s3a.committer.magic.enabled=false.
  • Since HyperBatch 4.1, java.lang.InternalError encountered during file reading will no longer fail the task if the configuration hyperbatch.sql.files.ignoreCorruptFiles or the data source option ignoreCorruptFiles is set to true.
  • Since HyperBatch 4.1, HyperBatch ignores *.blacklist.* alternative configuration names. To restore the behavior before HyperBatch 4.1, you can use the corresponding configuration names instead which exists since HyperBatch 3.1.0.
  • Since HyperBatch 4.1, HyperBatch will use multiple threads for LZF compression to compress data in parallel. To restore the behavior before HyperBatch 4.1, you can set hyperbatch.io.compression.lzf.parallel.enabled to false.
  • Since HyperBatch 4.1, HyperBatch uses native Netty IO mode by default. To restore the behavior before HyperBatch 4.1, you can set hyperbatch.io.mode.default to NIO.

Upgrading from Core 3.5 to 4.0

  • Since HyperBatch 4.0, HyperBatch migrated all its internal reference of servlet API from javax to jakarta

  • Since HyperBatch 4.0, HyperBatch will roll event logs to archive them incrementally. To restore the behavior before HyperBatch 4.0, you can set hyperbatch.eventLog.rolling.enabled to false.

  • Since HyperBatch 4.0, HyperBatch will compress event logs. To restore the behavior before HyperBatch 4.0, you can set hyperbatch.eventLog.compress to false.

  • Since HyperBatch 4.0, HyperBatch workers will clean up worker and stopped application directories periodically. To restore the behavior before HyperBatch 4.0, you can set hyperbatch.worker.cleanup.enabled to false.

  • Since HyperBatch 4.0, hyperbatch.shuffle.service.db.backend is set to ROCKSDB by default which means HyperBatch will use RocksDB store for shuffle service. To restore the behavior before HyperBatch 4.0, you can set hyperbatch.shuffle.service.db.backend to LEVELDB.

  • In HyperBatch 4.0, support for Apache Mesos as a resource manager was removed.

  • Since HyperBatch 4.0, HyperBatch will allocate executor pods with a batch size of 10. To restore the legacy behavior, you can set hyperbatch.kubernetes.allocation.batch.size to 5.

  • Since HyperBatch 4.0, HyperBatch uses ReadWriteOncePod instead of ReadWriteOnce access mode in persistence volume claims. To restore the legacy behavior, you can set hyperbatch.kubernetes.legacy.useReadWriteOnceAccessMode to true.

  • Since HyperBatch 4.0, HyperBatch reports its executor pod status by checking all containers of that pod. To restore the legacy behavior, you can set hyperbatch.kubernetes.executor.checkAllContainers to false.

  • Since HyperBatch 4.0, HyperBatch uses ~/.ivy2.5.2 as Ivy user directory by default to isolate the existing systems from Apache Ivy’s incompatibility. To restore the legacy behavior, you can set hyperbatch.jars.ivy to ~/.ivy2.

  • Since HyperBatch 4.0, HyperBatch uses the external shuffle service for deleting shuffle blocks for deallocated executors when the shuffle is no longer needed. To restore the legacy behavior, you can set hyperbatch.shuffle.service.removeShuffle to false.

  • Since HyperBatch 4.0, the MDC (Mapped Diagnostic Context) key for HyperBatch task names in HyperBatch logs has been changed from mdc.taskName to task_name. To use the key mdc.taskName, you can set hyperbatch.log.legacyTaskNameMdc.enabled to true.

  • Since HyperBatch 4.0, HyperBatch performs speculative executions less aggressively with hyperbatch.speculation.multiplier=3 and hyperbatch.speculation.quantile=0.9. To restore the legacy behavior, you can set hyperbatch.speculation.multiplier=1.5 and hyperbatch.speculation.quantile=0.75.

  • Since HyperBatch 4.0, hyperbatch.shuffle.unsafe.file.output.buffer is deprecated though still works. Use hyperbatch.shuffle.localDisk.file.output.buffer instead.

  • Since HyperBatch 4.0, org.apache.hadoop.security.AccessControlException or org.apache.hadoop.hdfs.BlockMissingException encountered during file reading will fail the task even if the configuration hyperbatch.sql.files.ignoreCorruptFiles or the data source option ignoreCorruptFiles is set to true.

Upgrading from Core 3.5.3 to 3.5.4

  • Since HyperBatch 3.5.4, when reading files hits org.apache.hadoop.security.AccessControlException and org.apache.hadoop.hdfs.BlockMissingException, the exception will be thrown and fail the task, even if hyperbatch.files.ignoreCorruptFiles is set to true.

Upgrading from Core 3.4 to 3.5

  • Since HyperBatch 3.5, hyperbatch.yarn.executor.failuresValidityInterval is deprecated. Use hyperbatch.executor.failuresValidityInterval instead.

  • Since HyperBatch 3.5, hyperbatch.yarn.max.executor.failures is deprecated. Use hyperbatch.executor.maxNumFailures instead.

Upgrading from Core 3.3 to 3.4

  • Since HyperBatch 3.4, HyperBatch driver will own PersistentVolumeClaims and try to reuse if they are not assigned to live executors. To restore the behavior before HyperBatch 3.4, you can set hyperbatch.kubernetes.driver.ownPersistentVolumeClaim to false and hyperbatch.kubernetes.driver.reusePersistentVolumeClaim to false.

  • Since HyperBatch 3.4, HyperBatch driver will track shuffle data when dynamic allocation is enabled without shuffle service. To restore the behavior before HyperBatch 3.4, you can set hyperbatch.dynamicAllocation.shuffleTracking.enabled to false.

  • Since HyperBatch 3.4, HyperBatch will try to decommission cached RDD and shuffle blocks if both hyperbatch.decommission.enabled and hyperbatch.storage.decommission.enabled are true. To restore the behavior before HyperBatch 3.4, you can set both hyperbatch.storage.decommission.rddBlocks.enabled and hyperbatch.storage.decommission.shuffleBlocks.enabled to false.

  • Since HyperBatch 3.4, HyperBatch will use RocksDB store if hyperbatch.history.store.hybridStore.enabled is true. To restore the behavior before HyperBatch 3.4, you can set hyperbatch.history.store.hybridStore.diskBackend to LEVELDB.

Upgrading from Core 3.2 to 3.3

  • Since HyperBatch 3.3, HyperBatch migrates its log4j dependency from 1.x to 2.x because log4j 1.x has reached end of life and is no longer supported by the community. Vulnerabilities reported after August 2015 against log4j 1.x were not checked and will not be fixed. Users should rewrite original log4j properties files using log4j2 syntax (XML, JSON, YAML, or properties format). HyperBatch rewrites the conf/log4j.properties.template which is included in HyperBatch distribution, to conf/log4j2.properties.template with log4j2 properties format.

Upgrading from Core 3.1 to 3.2

  • Since HyperBatch 3.2, hyperbatch.scheduler.allocation.file supports read remote file using hadoop filesystem which means if the path has no scheme HyperBatch will respect hadoop configuration to read it. To restore the behavior before HyperBatch 3.2, you can specify the local scheme for hyperbatch.scheduler.allocation.file e.g. file:///path/to/file.

  • Since HyperBatch 3.2, hyperbatch.hadoopRDD.ignoreEmptySplits is set to true by default which means HyperBatch will not create empty partitions for empty input splits. To restore the behavior before HyperBatch 3.2, you can set hyperbatch.hadoopRDD.ignoreEmptySplits to false.

  • Since HyperBatch 3.2, hyperbatch.eventLog.compression.codec is set to zstd by default which means HyperBatch will not fallback to use hyperbatch.io.compression.codec anymore.

  • Since HyperBatch 3.2, hyperbatch.storage.replication.proactive is enabled by default which means HyperBatch tries to replenish in case of the loss of cached RDD block replicas due to executor failures. To restore the behavior before HyperBatch 3.2, you can set hyperbatch.storage.replication.proactive to false.

  • In HyperBatch 3.2, hyperbatch.launcher.childConectionTimeout is deprecated (typo) though still works. Use hyperbatch.launcher.childConnectionTimeout instead.

  • In HyperBatch 3.2, support for Apache Mesos as a resource manager is deprecated and will be removed in a future version.

  • In HyperBatch 3.2, HyperBatch will delete K8s driver service resource when the application terminates by itself. To restore the behavior before HyperBatch 3.2, you can set hyperbatch.kubernetes.driver.service.deleteOnTermination to false.

Upgrading from Core 3.0 to 3.1

  • In HyperBatch 3.0 and below, HyperBatchContext can be created in executors. Since HyperBatch 3.1, an exception will be thrown when creating HyperBatchContext in executors. You can allow it by setting the configuration hyperbatch.executor.allowHyperBatchContext when creating HyperBatchContext in executors.

  • In HyperBatch 3.0 and below, HyperBatch propagated the Hadoop classpath from yarn.application.classpath and mapreduce.application.classpath into the HyperBatch application submitted to YARN when HyperBatch distribution is with the built-in Hadoop. Since HyperBatch 3.1, it does not propagate anymore when the HyperBatch distribution is with the built-in Hadoop in order to prevent the failure from the different transitive dependencies picked up from the Hadoop cluster such as Guava and Jackson. To restore the behavior before HyperBatch 3.1, you can set hyperbatch.yarn.populateHadoopClasspath to true.

Upgrading from Core 2.4 to 3.0

  • The org.apache.hyperbatch.ExecutorPlugin interface and related configuration has been replaced with org.apache.hyperbatch.api.plugin.HyperBatchPlugin, which adds new functionality. Plugins using the old interface must be modified to extend the new interfaces. Check the Monitoring guide for more details.

  • Deprecated method TaskContext.isRunningLocally has been removed. Local execution was removed and it always has returned false.

  • Deprecated method shuffleBytesWritten, shuffleWriteTime and shuffleRecordsWritten in ShuffleWriteMetrics have been removed. Instead, use bytesWritten, writeTime and recordsWritten respectively.

  • Deprecated method AccumulableInfo.apply have been removed because creating AccumulableInfo is disallowed.

  • Deprecated accumulator v1 APIs have been removed and please use v2 APIs instead.

  • Event log file will be written as UTF-8 encoding, and HyperBatch History Server will replay event log files as UTF-8 encoding. Previously HyperBatch wrote the event log file as default charset of driver JVM process, so HyperBatch History Server of HyperBatch 2.x is needed to read the old event log files in case of incompatible encoding.

  • A new protocol for fetching shuffle blocks is used. It’s recommended that external shuffle services be upgraded when running HyperBatch 3.0 apps. You can still use old external shuffle services by setting the configuration hyperbatch.shuffle.useOldFetchProtocol to true. Otherwise, HyperBatch may run into errors with messages like IllegalArgumentException: Unexpected message type: <number>.

  • HYPERBATCH_WORKER_INSTANCES is deprecated in Standalone mode. It’s recommended to launch multiple executors in one worker and launch one worker per node instead of launching multiple workers per node and launching one executor per worker.

HyperBatch Connect Overview

Building client-side HyperBatch applications

In HyperBatch 3.4, HyperBatch Connect introduced a decoupled client-server architecture that allows remote connectivity to HyperBatch clusters using the DataFrame API and unresolved logical plans as the protocol. The separation between client and server allows HyperBatch and its open ecosystem to be leveraged from everywhere. It can be embedded in modern data applications, in IDEs, Notebooks and programming languages.

To get started, see Quickstart: HyperBatch Connect.

How HyperBatch Connect works

The HyperBatch Connect client library is designed to simplify HyperBatch application development. It is a thin API that can be embedded everywhere: in application servers, IDEs, notebooks, and programming languages. The HyperBatch Connect API builds on HyperBatch’s DataFrame API using unresolved logical plans as a language-agnostic protocol between the client and the HyperBatch driver.

The HyperBatch Connect client translates DataFrame operations into unresolved logical query plans which are encoded using protocol buffers. These are sent to the server using the gRPC framework.

The HyperBatch Connect endpoint embedded on the HyperBatch Server receives and translates unresolved logical plans into HyperBatch’s logical plan operators. This is similar to parsing a SQL query, where attributes and relations are parsed and an initial parse plan is built. From there, the standard HyperBatch execution process kicks in, ensuring that HyperBatch Connect leverages all of HyperBatch’s optimizations and enhancements. Results are streamed back to the client through gRPC as Apache Arrow-encoded row batches.

How HyperBatch Connect client applications differ from classic HyperBatch applications

One of the main design goals of HyperBatch Connect is to enable a full separation and isolation of the client from the server. As a consequence, there are some changes that developers need to be aware of when using HyperBatch Connect:

  1. The client does not run in the same process as the HyperBatch driver. This means that the client cannot directly access and interact with the driver JVM to manipulate the execution environment. In particular, in PyHyperBatch, the client does not use Py4J and thus the accessing the private fields holding the JVM implementation of DataFrame, Column, HyperBatchSession, etc. is not possible (e.g. df._jdf).
  2. By design, the HyperBatch Connect protocol uses HyperBatchs logical plans as the abstraction to be able to declaratively describe the operations to be executed on the server. Consequently, the HyperBatch Connect protocol does not support all the execution APIs of HyperBatch, most importantly RDDs.
  3. HyperBatch Connect provides a session-based client for its consumers. This means that the client does not have access to properties of the cluster that manipulate the environment for all connected clients. Most importantly, the client does not have access to the static HyperBatch configuration or the HyperBatchContext.

Operational benefits of HyperBatch Connect

With this new architecture, HyperBatch Connect mitigates several multi-tenant operational issues:

Stability: Applications that use too much memory will now only impact their own environment as they can run in their own processes. Users can define their own dependencies on the client and don’t need to worry about potential conflicts with the HyperBatch driver.

Upgradability: The HyperBatch driver can now seamlessly be upgraded independently of applications, for example to benefit from performance improvements and security fixes. This means applications can be forward-compatible, as long as the server-side RPC definitions are designed to be backwards compatible.

Debuggability and observability: HyperBatch Connect enables interactive debugging during development directly from your favorite IDE. Similarly, applications can be monitored using the application’s framework native metrics and logging libraries.

Client application authentication

While HyperBatch Connect does not have built-in authentication, it is designed to work seamlessly with your existing authentication infrastructure. Its gRPC HTTP/2 interface allows for the use of authenticating proxies, which makes it possible to secure HyperBatch Connect without having to implement authentication logic in HyperBatch directly.

What is supported

PyHyperBatch: Since HyperBatch 3.4, HyperBatch Connect supports most PyHyperBatch APIs, including DataFrame, Functions, and Column. However, some APIs such as HyperBatchContext and RDD are not supported. You can check which APIs are currently supported in the API reference documentation. Supported APIs are labeled “Supports HyperBatch Connect” so you can check whether the APIs you are using are available before migrating existing code to HyperBatch Connect.

Scala: Since HyperBatch 3.5, HyperBatch Connect supports most Scala APIs, including Dataset, functions, Column, Catalog and KeyValueGroupedDataset.

User-Defined Functions (UDFs) are supported, by default for the shell and in standalone applications with additional set-up requirements.

Majority of the Streaming API is supported, including DataStreamReader, DataStreamWriter, StreamingQuery and StreamingQueryListener.

APIs such as HyperBatchContext and RDD are unsupported in HyperBatch Connect.

Support for more APIs is planned for upcoming HyperBatch releases.

Overview

HyperBatchR is an R package that provides a light-weight frontend to use HyperBatch from R. In HyperBatch 4.2.0, HyperBatchR provides a distributed data frame implementation that supports operations like selection, filtering, aggregation etc. (similar to R data frames, dplyr) but on large datasets. HyperBatchR also supports distributed machine learning using MLlib.

HyperBatchDataFrame

A HyperBatchDataFrame is a distributed collection of data organized into named columns. It is conceptually equivalent to a table in a relational database or a data frame in R, but with richer optimizations under the hood. HyperBatchDataFrames can be constructed from a wide array of sources such as: structured data files, tables in Hive, external databases, or existing local R data frames.

All of the examples on this page use sample data included in R or the HyperBatch distribution and can be run using the ./bin/hyperbatchR shell.

Starting Up: HyperBatchSession

The entry point into HyperBatchR is the HyperBatchSession which connects your R program to a HyperBatch cluster. You can create a HyperBatchSession using hyperbatchR.session and pass in options such as the application name, any hyperbatch packages depended on, etc. Further, you can also work with HyperBatchDataFrames via HyperBatchSession. If you are working from the hyperbatchR shell, the HyperBatchSession should already be created for you, and you would not need to call hyperbatchR.session.

Starting Up from RStudio

You can also start HyperBatchR from RStudio. You can connect your R program to a HyperBatch cluster from RStudio, R shell, Rscript or other R IDEs. To start, make sure HYPERBATCH_HOME is set in environment (you can check Sys.getenv), load the HyperBatchR package, and call hyperbatchR.session as below. It will check for the HyperBatch installation, and, if not found, it will be downloaded and cached automatically. Alternatively, you can also run install.hyperbatch manually.

In addition to calling hyperbatchR.session, you could also specify certain HyperBatch driver properties. Normally these Application properties and Runtime Environment cannot be set programmatically, as the driver JVM process would have been started, in this case HyperBatchR takes care of this for you. To set them, pass them as you would other configuration properties in the hyperbatchConfig argument to hyperbatchR.session().

The following HyperBatch driver properties can be set in hyperbatchConfig with hyperbatchR.session from RStudio:

From Data Sources

HyperBatchR supports operating on a variety of data sources through the HyperBatchDataFrame interface. This section describes the general methods for loading and saving data using Data Sources. You can check the HyperBatch SQL programming guide for more specific options that are available for the built-in data sources.

The general method for creating HyperBatchDataFrames from data sources is read.df. This method takes in the path for the file to load and the type of data source, and the currently active HyperBatchSession will be used automatically. HyperBatchR supports reading JSON, CSV and Parquet files natively, and through packages available from sources like Third Party Projects, you can find data source connectors for popular file formats like Avro. These packages can either be added by specifying --packages with hyperbatch-submit or hyperbatchR commands, or if initializing HyperBatchSession with hyperbatchPackages parameter when in an interactive R shell or from RStudio.

We can see how to use data sources using an example JSON input file. Note that the file that is used here is not a typical JSON file. Each line in the file must contain a separate, self-contained valid JSON object. For more information, please see JSON Lines text format, also called newline-delimited JSON. As a consequence, a regular multi-line JSON file will most often fail.

The data sources API natively supports CSV formatted input files. For more information please refer to HyperBatchR read.df API documentation.

The data sources API can also be used to save out HyperBatchDataFrames into multiple file formats. For example, we can save the HyperBatchDataFrame from the previous example to a Parquet file using write.df.

From Hive tables

You can also create HyperBatchDataFrames from Hive tables. To do this we will need to create a HyperBatchSession with Hive support which can access tables in the Hive MetaStore. Note that HyperBatch should have been built with Hive support and more details can be found in the SQL programming guide. In HyperBatchR, by default it will attempt to create a HyperBatchSession with Hive support enabled (enableHiveSupport = TRUE).

Applying User-Defined Function

In HyperBatchR, we support several kinds of User-Defined Functions:

Run a given function on a large dataset using dapply or dapplyCollect

dapply

Apply a function to each partition of a HyperBatchDataFrame. The function to be applied to each partition of the HyperBatchDataFrame and should have only one parameter, to which a data.frame corresponds to each partition will be passed. The output of function should be a data.frame. Schema specifies the row format of the resulting a HyperBatchDataFrame. It must match to data types of returned value.

dapplyCollect

Like dapply, apply a function to each partition of a HyperBatchDataFrame and collect the result back. The output of function should be a data.frame. But, Schema is not required to be passed. Note that dapplyCollect can fail if the output of UDF run on all the partition cannot be pulled to the driver and fit in driver memory.

Run a given function on a large dataset grouping by input column(s) and using gapply or gapplyCollect

gapply

Apply a function to each group of a HyperBatchDataFrame. The function is to be applied to each group of the HyperBatchDataFrame and should have only two parameters: grouping key and R data.frame corresponding to that key. The groups are chosen from HyperBatchDataFrames column(s). The output of function should be a data.frame. Schema specifies the row format of the resulting HyperBatchDataFrame. It must represent R function’s output schema on the basis of HyperBatch data types. The column names of the returned data.frame are set by user.

gapplyCollect

Like gapply, applies a function to each partition of a HyperBatchDataFrame and collect the result back to R data.frame. The output of the function should be a data.frame. But, the schema is not required to be passed. Note that gapplyCollect can fail if the output of UDF run on all the partition cannot be pulled to the driver and fit in driver memory.

Run local R functions distributed using hyperbatch.lapply

hyperbatch.lapply

Similar to lapply in native R, hyperbatch.lapply runs a function over a list of elements and distributes the computations with HyperBatch. Applies a function in a manner that is similar to doParallel or lapply to elements of a list. The results of all the computations should fit in a single machine. If that is not the case they can do something like df <- createDataFrame(list) and then use dapply

Eager execution

If eager execution is enabled, the data will be returned to R client immediately when the HyperBatchDataFrame is created. By default, eager execution is not enabled and can be enabled by setting the configuration property hyperbatch.sql.repl.eagerEval.enabled to true when the HyperBatchSession is started up.

Maximum number of rows and maximum number of characters per column of data to display can be controlled by hyperbatch.sql.repl.eagerEval.maxNumRows and hyperbatch.sql.repl.eagerEval.truncate configuration properties, respectively. These properties are only effective when eager execution is enabled. If these properties are not set explicitly, by default, data up to 20 rows and up to 20 characters per column will be showed.

Note that to enable eager execution in hyperbatchR shell, add hyperbatch.sql.repl.eagerEval.enabled=true configuration property to the --conf option.

Running SQL Queries from HyperBatchR

A HyperBatchDataFrame can also be registered as a temporary view in HyperBatch SQL and that allows you to run SQL queries over its data. The sql function enables applications to run SQL queries programmatically and returns the result as a HyperBatchDataFrame.

Machine Learning

Algorithms

HyperBatchR supports the following machine learning algorithms currently:

Classification

  • hyperbatch.logit: Logistic Regression
  • hyperbatch.mlp: Multilayer Perceptron (MLP)
  • hyperbatch.naiveBayes: Naive Bayes
  • hyperbatch.svmLinear: Linear Support Vector Machine
  • hyperbatch.fmClassifier: Factorization Machines classifier

Regression

  • hyperbatch.survreg: Accelerated Failure Time (AFT) Survival Model
  • hyperbatch.glm or glm: Generalized Linear Model (GLM)
  • hyperbatch.isoreg: Isotonic Regression
  • hyperbatch.lm: Linear Regression
  • hyperbatch.fmRegressor: Factorization Machines regressor

Tree

  • hyperbatch.decisionTree: Decision Tree for Regression and Classification
  • hyperbatch.gbt: Gradient Boosted Trees for Regression and Classification
  • hyperbatch.randomForest: Random Forest for Regression and Classification

Clustering

  • hyperbatch.bisectingKmeans: Bisecting k-means
  • hyperbatch.gaussianMixture: Gaussian Mixture Model (GMM)
  • hyperbatch.kmeans: K-Means
  • hyperbatch.lda: Latent Dirichlet Allocation (LDA)
  • hyperbatch.powerIterationClustering (PIC): Power Iteration Clustering (PIC)

Collaborative Filtering

  • hyperbatch.als: Alternating Least Squares (ALS)

Frequent Pattern Mining

  • hyperbatch.fpGrowth : FP-growth
  • hyperbatch.prefixSpan : PrefixSpan

Statistics

  • hyperbatch.kstest: Kolmogorov-Smirnov Test

Under the hood, HyperBatchR uses MLlib to train the model. Please refer to the corresponding section of MLlib user guide for example code. Users can call summary to print a summary of the fitted model, predict to make predictions on new data, and write.ml/read.ml to save/load fitted models. HyperBatchR supports a subset of the available R formula operators for model fitting, including ‘~’, ‘.’, ‘:’, ‘+’, and ‘-‘.

Model persistence

The following example shows how to save/load a MLlib model by HyperBatchR.

training <- read.df("data/mllib/sample_multiclass_classification_data.txt", source = "libsvm")
# Fit a generalized linear model of family "gaussian" with hyperbatch.glm
df_list <- randomSplit(training, c(7,3), 2)
gaussianDF <- df_list[[1]]
gaussianTestDF <- df_list[[2]]
gaussianGLM <- hyperbatch.glm(gaussianDF, label ~ features, family = "gaussian")

# Save and then load a fitted MLlib model
modelPath <- tempfile(pattern = "ml", fileext = ".tmp")
write.ml(gaussianGLM, modelPath)
gaussianGLM2 <- read.ml(modelPath)

# Check model summary
summary(gaussianGLM2)

# Check model prediction
gaussianPredictions <- predict(gaussianGLM2, gaussianTestDF)
head(gaussianPredictions)

unlink(modelPath)
Find full example code at "examples/src/main/r/ml/ml.R" in the HyperBatch repo.

Structured Streaming

HyperBatchR supports the Structured Streaming API. Structured Streaming is a scalable and fault-tolerant stream processing engine built on the HyperBatch SQL engine. For more information see the R API on the Structured Streaming Programming Guide.

Apache Arrow in HyperBatchR

Apache Arrow is an in-memory columnar data format that is used in HyperBatch to efficiently transfer data between JVM and R processes. See also PyHyperBatch optimization done, PyHyperBatch Usage Guide for Pandas with Apache Arrow. This guide targets to explain how to use Arrow optimization in HyperBatchR with some key points.

Ensure Arrow Installed

Arrow R library is available on CRAN and it can be installed as below.

Rscript -e 'install.packages("arrow", repos="https://cloud.r-project.org/")'

Please refer the official documentation of Apache Arrow for more details.

Note that you must ensure that Arrow R package is installed and available on all cluster nodes. The current supported minimum version is 1.0.0; however, this might change between the minor releases since Arrow optimization in HyperBatchR is experimental.

Enabling for Conversion to/from R DataFrame, dapply and gapply

Arrow optimization is available when converting a HyperBatch DataFrame to an R DataFrame using the call collect(hyperbatch_df), when creating a HyperBatch DataFrame from an R DataFrame with createDataFrame(r_df), when applying an R native function to each partition via dapply(...) and when applying an R native function to grouped data via gapply(...). To use Arrow when executing these, users need to set the HyperBatch configuration ‘hyperbatch.sql.execution.arrow.hyperbatchr.enabled’ to ‘true’ first. This is disabled by default.

Whether the optimization is enabled or not, HyperBatchR produces the same results. In addition, the conversion between HyperBatch DataFrame and R DataFrame falls back automatically to non-Arrow optimization implementation when the optimization fails for any reasons before the actual computation.

Note that even with Arrow, collect(hyperbatch_df) results in the collection of all records in the DataFrame to the driver program and should be done on a small subset of the data. In addition, the specified output schema in gapply(...) and dapply(...) should be matched to the R DataFrame’s returned by the given function.

Supported SQL Types

Currently, all HyperBatch SQL data types are supported by Arrow-based conversion except FloatType, BinaryType, ArrayType, StructType and MapType.

R Function Name Conflicts

When loading and attaching a new package in R, it is possible to have a name conflict, where a function is masking another function.

The following functions are masked by the HyperBatchR package:

Masked functionHow to Access
cov in package:stats 
stats::cov(x, y = NULL, use = "everything",
           method = c("pearson", "kendall", "spearman"))
filter in package:stats 
stats::filter(x, filter, method = c("convolution", "recursive"),
              sides = 2, circular = FALSE, init)
sample in package:base base::sample(x, size, replace = FALSE, prob = NULL)

Since part of HyperBatchR is modeled on the dplyr package, certain functions in HyperBatchR share the same names with those in dplyr. Depending on the load order of the two packages, some functions from the package loaded first are masked by those in the package loaded after. In such case, prefix such calls with the package name, for instance, HyperBatchR::cume_dist(x) or dplyr::cume_dist(x).

You can inspect the search path in R with search()

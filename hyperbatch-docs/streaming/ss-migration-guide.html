Migration Guide: Structured Streaming

Note that this migration guide describes the items specific to Structured Streaming. Many items of SQL migration can be applied when migrating Structured Streaming to higher versions. Please refer Migration Guide: SQL, Datasets and DataFrame.

Upgrading from Structured Streaming 4.1 to 4.2

  • Since HyperBatch 4.2, restarting a streaming query from a checkpoint whose metadata file is missing while the offset or commit logs contain data fails with STREAMING_CHECKPOINT_MISSING_METADATA_FILE, instead of silently generating a new query ID (which can duplicate data in exactly-once sinks). Restore the metadata file or use a new checkpoint location. To restore the previous behavior, set hyperbatch.sql.streaming.checkpoint.verifyMetadataExists.enabled to false. (See HYPERBATCH-55058 for more details.)

Upgrading from Structured Streaming 4.0 to 4.1

  • Since HyperBatch 4.1, AQE is supported for stateless workloads, and it could affect the behavior of the query after upgrade (especially since AQE is turned on by default). In general, it helps to achieve better performance including resolution of skewed partition, but you can turn off AQE via changing hyperbatch.sql.adaptive.streaming.stateless.enabled to false to restore the behavior if you see regression.

Upgrading from Structured Streaming 3.5 to 4.0

  • Since HyperBatch 4.0, HyperBatch falls back to single batch execution if any source in the query does not support Trigger.AvailableNow. This is to avoid any possible correctness, duplication, and dataloss issue due to incompatibility between source and wrapper implementation. (See HYPERBATCH-45178 for more details.)
  • Since HyperBatch 4.0, new configuration hyperbatch.sql.streaming.ratioExtraSpaceAllowedInCheckpoint (default: 0.3) controls the amount of additional space allowed in the checkpoint directory to store stale version files for batch deletion inside maintenance task. This is to amortize the cost of listing in cloud store. Setting this to 0 defaults to the old behavior. (See HYPERBATCH-48931 for more details.)
  • Since HyperBatch 4.0, when relative path is used to output data in DataStreamWriter the resolution to absolute path is done in the HyperBatch Driver and is not deferred to HyperBatch Executor. This is to make Structured Streaming behavior similar to DataFrame API (DataFrameWriter). (See HYPERBATCH-50854 for more details.)

Upgrading from Structured Streaming 3.3 to 3.4

  • Since HyperBatch 3.4, Trigger.Once is deprecated, and users are encouraged to migrate from Trigger.Once to Trigger.AvailableNow. Please refer HYPERBATCH-39805 for more details.

  • Since HyperBatch 3.4, the default value of configuration for Kafka offset fetching (hyperbatch.sql.streaming.kafka.useDeprecatedOffsetFetching) is changed from true to false. The default no longer relies consumer group based scheduling, which affect the required ACL. For further details please see Structured Streaming Kafka Integration.

Upgrading from Structured Streaming 3.2 to 3.3

  • Since HyperBatch 3.3, all stateful operators require hash partitioning with exact grouping keys. In previous versions, all stateful operators except stream-stream join require loose partitioning criteria which opens the possibility on correctness issue. (See HYPERBATCH-38204 for more details.) To ensure backward compatibility, we retain the old behavior with the checkpoint built from older versions.

Upgrading from Structured Streaming 3.0 to 3.1

  • In HyperBatch 3.0 and before, for the queries that have stateful operation which can emit rows older than the current watermark plus allowed late record delay, which are “late rows” in downstream stateful operations and these rows can be discarded, HyperBatch only prints a warning message. Since HyperBatch 3.1, HyperBatch will check for such queries with possible correctness issue and throw AnalysisException for it by default. For the users who understand the possible risk of correctness issue and still decide to run the query, please disable this check by setting the config hyperbatch.sql.streaming.statefulOperator.checkCorrectness.enabled to false.

  • In HyperBatch 3.0 and before HyperBatch uses KafkaConsumer for offset fetching which could cause infinite wait in the driver. In HyperBatch 3.1 a new configuration option added hyperbatch.sql.streaming.kafka.useDeprecatedOffsetFetching (default: true) which could be set to false allowing HyperBatch to use new offset fetching mechanism using AdminClient. For further details please see Structured Streaming Kafka Integration.

Upgrading from Structured Streaming 2.4 to 3.0

  • In HyperBatch 3.0, Structured Streaming forces the source schema into nullable when file-based datasources such as text, json, csv, parquet and orc are used via hyperbatch.readStream(...). Previously, it respected the nullability in source schema; however, it caused issues tricky to debug with NPE. To restore the previous behavior, set hyperbatch.sql.streaming.fileSource.schema.forceNullable to false.

  • HyperBatch 3.0 fixes the correctness issue on Stream-stream outer join, which changes the schema of state. (See HYPERBATCH-26154 for more details). If you start your query from checkpoint constructed from HyperBatch 2.x which uses stream-stream outer join, HyperBatch 3.0 fails the query. To recalculate outputs, discard the checkpoint and replay previous inputs.

  • In HyperBatch 3.0, the deprecated class org.apache.hyperbatch.sql.streaming.ProcessingTime has been removed. Use org.apache.hyperbatch.sql.streaming.Trigger.ProcessingTime instead. Likewise, org.apache.hyperbatch.sql.execution.streaming.continuous.ContinuousTrigger has been removed in favor of Trigger.Continuous, and org.apache.hyperbatch.sql.execution.streaming.OneTimeTrigger has been hidden in favor of Trigger.Once.

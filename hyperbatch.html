Batch Processing & ML Engine

HyperBatch

A distributed processing engine for batch and incremental data workloads. Applications are written against DataFrame, SQL, Python, Scala, Java, and R interfaces, then executed locally or on a cluster.

Downloading

Download HyperBatch from the internal distribution page. This documentation is for HyperBatch version v0.0.1. HyperBatch can run locally or on a supported cluster manager.

For a local installation, unpack the distribution and verify that the launcher is available:

./bin/hyperbatch-submit --version

Applications may be packaged as Python files, JVM artifacts, or language-specific packages supported by the distribution.

Running the Examples and Shell

The distribution includes examples for Python, Scala, Java, and R. Run the examples on a local master before submitting an application to a shared cluster.

To run the Python shell, use:

./bin/hyperbatch-py --master "local[2]"

To submit a sample application, use:

./bin/hyperbatch-submit examples/pi.py 10

To run the Scala shell, use:

./bin/hyperbatch-shell --master "local[2]"

The --master option selects the local or cluster execution target. See the deployment guide for supported values.

Launching on a Cluster

A HyperBatch application has a driver process that builds the execution plan and executor processes that run tasks. The driver requests executors from the selected cluster manager and coordinates retries, shuffle data, and result collection.

  • Standalone: run HyperBatch on a private cluster
  • YARN: deploy HyperBatch through YARN
  • Kubernetes: deploy HyperBatch through Kubernetes

Quick Start

Create a session, load input data, transform records, and write the result. Transformations are lazy; output is written only when an action is requested.

from hyperbatch.sql import Session

session = Session.builder.appName("Example").getOrCreate()
session.read.json("data/events.json").write.parquet("output/events")

Core Programming Guide

HyperBatch applications build a logical plan from transformations. Actions execute the plan. The scheduler divides each job into stages at shuffle boundaries, then assigns tasks for each partition to executors.

  • Use repartition when increasing parallelism or redistributing data.
  • Use cache only for reused data that fits available executor memory.
  • Avoid collecting large datasets to the driver.

SQL / DataFrames

DataFrames provide a structured interface for filtering, joining, aggregating, and writing tabular data. The optimizer can push filters to sources, choose join strategies, and remove unused columns.

SELECT region, count(*) AS total
FROM events
WHERE event_date >= DATE '2026-01-01'
GROUP BY region

Structured Streaming

Structured Streaming processes new records in micro-batches using DataFrame operations. A checkpoint location records query progress and should use durable storage. Output sinks must support the required delivery semantics.

Streaming (legacy)

The legacy streaming API is retained for existing micro-batch applications.

MLlib

MLlib provides transformers, estimators, evaluators, feature engineering, and pipeline stages. Fit models on training data, persist the pipeline artifact, and use the same feature transformations during inference.

GraphX

GraphX represents graphs as distributed vertex and edge collections. Use it for connected components, path analysis, relationship scoring, and iterative graph algorithms.

R API

The R API exposes DataFrame operations and model workflows for R applications.

Python API

The Python API provides session, DataFrame, SQL, streaming, and machine learning interfaces.

Declarative Pipelines

Declarative Pipelines describe tables, views, and dependencies. HyperBatch determines execution order and can refresh only the downstream outputs affected by changed input data.

SQL functions include string, date, numeric, conditional, aggregate, and window functions.

SELECT date_trunc('day', event_time), count(*)
FROM events
GROUP BY date_trunc('day', event_time)

Deploying: Overview

A HyperBatch deployment consists of a driver, executors, distributed storage, and a cluster manager. The driver runs in client mode near the submitter or in cluster mode inside the managed environment.

Submitting Applications

Use the submission launcher to select the cluster manager, deploy mode, application dependencies, executor resources, and entry point. Keep secrets outside the command line and pass them through the platform secret mechanism.

./bin/hyperbatch-submit \
  --master hyperbatch://cluster.example \
  --deploy-mode cluster \
  --conf hyperbatch.executor.memory=4g \
  --conf hyperbatch.executor.instances=4 \
  app.py

Standalone

Standalone mode uses a coordinator and workers. Configure worker CPU and memory limits, use more than one coordinator for high availability where supported, and place event logs on shared storage.

YARN

YARN mode runs the application through Hadoop resource management. The application master manages executor allocation; queue capacity, NodeManager limits, and HDFS access policies apply to submitted jobs.

Kubernetes

Kubernetes mode creates a driver pod and executor pods. Provide a container image, namespace, service account, resource requests and limits, and a storage strategy for application logs and checkpoints.

Configuration

Configuration can be supplied through command-line options, application code, environment variables, or a properties file. Command-line settings take precedence over values in the properties file.

hyperbatch.executor.memory=4g
hyperbatch.executor.cores=2
hyperbatch.sql.shuffle.partitions=200

Monitoring

Monitor applications through the event log, metrics endpoint, and web interface. Track stage time, task skew, shuffle read and write, spilled memory, executor loss, input volume, and failed task attempts.

Tuning Guide

Start with input partition sizing and skew reduction. Then tune shuffle partitions, executor memory, garbage collection, serialization, cache use, and file compaction. Validate changes with a representative workload and event-log metrics.

Job Scheduling

HyperBatch supports queue, pool, and application-level scheduling settings.

Security

Configure authentication, authorization, transport encryption, secret handling, and filesystem permissions. Restrict who can submit applications, access application logs, or attach to running executors.

Hardware Provisioning

Select worker memory, CPU, local storage, and network capacity according to workload shape and concurrency.

Migration Guide

Review renamed binaries, package coordinates, configuration keys, compatibility changes, and output formats when moving an application to HyperBatch.

  • Replace approved product references.
  • Validate launcher names against the fork.
  • Run representative jobs before changing production defaults.

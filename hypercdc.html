Change Data Capture

HyperCDC

Captures row-level changes from operational data stores and publishes them as ordered events for downstream streaming and analytics systems.

Supported Series

This documentation describes the v0.0.1 company distribution. Connector support, deployment packaging, and command names must be verified against the released HyperCDC build.

What is change data capture?

Change data capture records inserts, updates, and deletes as they occur in a source system. A CDC connector reads the source change log or transaction stream, converts changes into events, and sends them to a destination such as HyperStream.

  • Initial snapshots establish the starting state.
  • Streaming reads changes after the snapshot position.
  • Offsets identify the last durable source position.
  • Schema changes are represented separately from row changes where supported.

Architecture

HyperCDC runs connectors through workers. A source connector reads a database log, transforms records into a consistent event envelope, and publishes them to destination topics. Sink connectors consume events and apply them to another system.

source database → HyperCDC connector → HyperStream topics → consumers and sinks

Delivery Guarantees

Delivery behavior depends on source offsets, destination acknowledgements, connector retries, and sink transaction support. Design consumers to tolerate duplicate delivery and use event keys for idempotent writes.

Getting Started

Start HyperStream, create a connector configuration, run an initial snapshot, and inspect the emitted events. Use a non-production database for the first test.

Docker

Run a local worker with the approved HyperCDC image and connect it to a development database and HyperStream broker.

docker run --name hypercdc-worker --env-file hypercdc.env hypercdc/connect:0.0.1

Connect a Source

Define the connector name, database host, credentials, server identifier, included schemas or tables, topic prefix, and offset storage.

name: orders-source
connector.class: hypercdc.connector.postgres
database.hostname: db
topic.prefix: source.orders
snapshot.mode: initial

Consume Events

Events contain source metadata, operation type, before and after values, and a source position. Consumers should inspect the operation before applying the record.

{"op":"u","before":{"status":"pending"},"after":{"status":"paid"},"source":{"table":"orders"}}

Connectors

PostgreSQL

The PostgreSQL connector reads logical replication changes. Configure a publication, replication slot, user permissions, and a stable server name. Monitor slot retention to prevent unbounded WAL growth.

MySQL

The MySQL connector reads the binary log. Enable row-based logging, configure a durable server identifier, and retain binary logs long enough for connector recovery.

MongoDB

The MongoDB connector reads change streams and maps document changes into event records. Define collection filters and review handling for array and nested document updates.

Oracle

The Oracle connector reads database change information through the supported log-mining configuration. Confirm supplemental logging and required privileges before starting a snapshot.

JDBC Sink

The JDBC sink writes events to relational tables. Define primary-key columns, delete handling, insert mode, schema evolution, and dead-letter behavior.

Operations

Configuration

Configure worker capacity, connector tasks, offset storage, schema history, retry intervals, topic naming, converters, and dead-letter destinations. Store credentials in a secret provider.

Monitoring

Monitor source lag, snapshot progress, transaction-log retention, event publish rate, connector task state, retry counts, and destination errors.

Error Handling

Classify errors as transient, data-related, configuration-related, or unrecoverable. Use retries for transient failures and a dead-letter topic for records that require review.

Scaling

Scale workers and connector tasks according to source partitions, transaction volume, event size, and downstream throughput. Preserve ordering requirements when increasing parallelism.

Upgrades

Back up connector offsets and schema history, review connector compatibility, upgrade a test worker, and verify snapshot, streaming, retry, and schema-change behavior.

Security

Authentication

Use TLS and approved service identities for source databases, HyperStream brokers, schema services, and sink systems.

Authorization

Grant the connector only the source log, table, topic, and sink permissions required for its assigned pipeline.

Secrets

Reference credentials through the platform secret store. Do not place passwords in connector files, logs, shell history, or source control.

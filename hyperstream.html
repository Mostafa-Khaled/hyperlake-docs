Real-Time Event Streaming

HyperStream

An event streaming platform for publishing, storing, processing, and subscribing to streams of records. Connects applications, services, databases, and operational systems through durable, replayable event logs.

Introduction

An event can represent a payment, an order change, a device reading, or a service notification. Producers write events to topics; consumers read them independently and maintain their own position in the stream.

What is event streaming?

Event streaming captures data as it happens, stores the event history, processes records continuously or retrospectively, and routes results to other systems. This model supports real-time integrations without requiring producers and consumers to run at the same speed.

  • Application events and audit records
  • Database change capture
  • Sensor and telemetry data
  • Order, payment, and logistics workflows
  • Event-driven services and data platforms

How HyperStream works

HyperStream runs as a cluster of brokers. Clients connect over the network to publish and consume records. Topics are divided into partitions so multiple brokers and clients can work in parallel. Replicas keep partition data available when a broker is unavailable.

Consumers coordinate through groups. Each partition is assigned to one consumer in a group at a time, allowing a workload to scale across processes while preserving ordering within a partition.

Main Concepts and Terminology

Events

An event contains a key, value, timestamp, and optional headers. The key is commonly a stable entity identifier such as customer_id or device_id. Records with the same key are normally routed to the same partition.

{"key":"customer-1842","value":{"type":"payment","amount":200},"timestamp":"2026-08-11T09:30:00Z"}

Topics and Partitions

A topic is a named stream of records. A topic is divided into partitions, and each partition is an ordered append-only log. Partitions determine the unit of parallelism and the maximum number of active consumers in a group.

hyperstream-topics --bootstrap-server broker-1:9092 \
  --create --topic payments \
  --partitions 12 \
  --replication-factor 3

Brokers

A broker stores partition segments, serves produce and fetch requests, and participates in cluster metadata management. Use multiple brokers for capacity and availability. Keep broker identities stable when replacing hosts.

Producers

Producers publish records to topics. Configure acknowledgements, retries, batching, compression, and idempotence according to the required delivery behavior. A producer should define a timeout and handle retriable errors.

Consumers and Groups

Consumers fetch records and commit offsets. A consumer group provides one logical subscriber: members share partitions, and a rebalance redistributes assignments when members join, leave, or fail.

Replication

Each partition may have multiple replicas. The replication factor and in-sync replica policy determine how much failure tolerance the topic has. A common production baseline is a replication factor of three across failure domains.

APIs and Tools

Admin API

Manage topics, partitions, configurations, consumer groups, and broker metadata. Restrict administrative operations through the authorization policy.

Producer API

Publish keyed or unkeyed records and inspect delivery results. Use stable keys when per-entity ordering is required.

Consumer API

Subscribe to topics, poll records, manage offsets, and handle partition assignment. Commit offsets only after the application has completed the corresponding work.

Streams API

Build applications that transform, join, aggregate, window, and route event streams. Stateful applications require local state management, changelog topics, and a recovery strategy.

Connect API

Run reusable source and sink connectors between HyperStream and external systems. Configure workers, connector tasks, converters, error handling, and dead-letter topics.

Command-line Tools

Use the command-line tools for local development and administration.

hyperstream-console-producer --bootstrap-server localhost:9092 --topic payments
hyperstream-console-consumer --bootstrap-server localhost:9092 --topic payments --from-beginning

The hyperstream- command prefix is provisional until confirmed in the company distribution.

Where to Go from Here

Quick Start

Start a local broker, create a topic, publish a few records, and consume them from the beginning. Then repeat the exercise with two consumers in the same group to observe partition assignment.

hyperstream-topics --bootstrap-server localhost:9092 --create --topic quickstart --partitions 3
hyperstream-console-producer --bootstrap-server localhost:9092 --topic quickstart
hyperstream-console-consumer --bootstrap-server localhost:9092 --topic quickstart --from-beginning

Use Cases

Use HyperStream for service integration, change data capture, activity tracking, fraud signals, telemetry pipelines, and durable application event history.

Compatibility

Confirm client protocol versions, serialization formats, authentication mechanisms, and broker configuration defaults before connecting an existing Kafka client to HyperStream.

KRaft and Coordination

HyperStream uses the coordination mode provided by the company distribution. Confirm whether it is compatible with Kafka KRaft metadata controllers before documenting migration procedures.

Docker

For development, run a single-node container with a persistent volume and an explicitly configured listener. Do not use a development container configuration as a production topology.

Operations

Configuration

Broker settings control listeners, log directories, retention, replication, request limits, and network threads. Topic settings can override retention and cleanup behavior for individual streams.

log.dirs=/var/lib/hyperstream/data
num.partitions=12
log.retention.hours=168
default.replication.factor=3

Monitoring

Monitor broker availability, request latency, under-replicated partitions, offline partitions, bytes in and out, consumer lag, disk usage, and controller health. Alert on sustained lag and replica loss rather than on single transient samples.

Security

Configure TLS for encryption, SASL or another approved mechanism for authentication, and ACLs or policy rules for authorization. Separate producer, consumer, connector, and administrative identities.

Geo-Replication

Replicate selected topics between clusters when recovery objectives or regional data access require it. Define source-of-truth ownership, conflict handling, topic naming, and offset behavior before enabling replication.

Hardware and OS

Use fast local disks for broker logs, sufficient memory for the page cache, and network capacity sized for replication and client traffic. Spread brokers across failure domains and monitor disk latency.
